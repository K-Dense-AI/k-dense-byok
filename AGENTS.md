# AGENTS.md

Guidance for coding agents (Claude Code loads it via `CLAUDE.md`) working in this repository.

## Project overview

K-Dense BYOK is a local AI research-assistant app ("Kady") that brings the user's own model credentials (API keys or supported subscriptions). It runs natively on macOS, Linux, and Windows. It is one repo with **two** runtime services started together by the cross-platform launcher `start.mjs` (wrapped by `./start.sh` on macOS/Linux and `start.cmd` on Windows):

| Service | Port | Code |
|---|---|---|
| Frontend (Next.js 16 / React 19) | 3000 | `web/` |
| Backend (TypeScript + Pi coding-agent SDK) | 8000 | `server/` |

The backend embeds the **Pi SDK** (`@earendil-works/pi-coding-agent`) and runs a **single flat agent** with built-in tools (`read`/`bash`/`edit`/`write`/`grep`/`find`/`ls`), a `subagent`/`bg_wait` delegation pair (the [pi-subagents](https://github.com/nicobailon/pi-subagents) extension package), an `interview` clarifying-questions tool (a native re-implementation of [pi-interview](https://pi.dev/packages/pi-interview) — see `server/src/agent/interview.ts`; the form renders inline in the chat UI instead of the package's own browser window), the [pi-web-access](https://pi.dev/packages/pi-web-access) web tools (`web_search`/`fetch_content`/`get_search_content`/`source_check`), live PDF annotation tools (`add_pdf_annotation`/`list_pdf_annotations`/`remove_pdf_annotation`), a hybrid durable Modal tool family (`modal_run`/`modal_submit`/`modal_status`/`modal_wait`/`modal_cancel`/`modal_results`/`modal_submit_batch`; `server/src/agent/modal-tool.ts`), and per-project MCP tools (`.pi/mcp.json`). PDF annotations and Modal jobs are also available to child agents through the vendored `kady-pdf-annotations` and `kady-modal` Pi packages; annotation sidecars use a shared cross-process lock and atomic replacement. Modal jobs are server-owned and restart-recoverable. There is no orchestrator/expert split and no model proxy: models go directly to **OpenRouter**, connected Pi OAuth providers (`openai-codex`, `anthropic`, `github-copilot`, `xai`), **NVIDIA NIM** (API key), or a local **Ollama** / OpenAI-compatible server. Everything runs locally; user data lives in `projects/`.

## Commands

Backend (`cd server` first; Node ≥ 22.19 recommended):

```bash
npm install                 # install deps
npm run dev                 # tsx watch on port 8000
npm run start               # run backend (tsx)
npm run prep                # ensure default project + seed scientific skills
npm run typecheck           # tsc --noEmit
npm test                    # vitest
```

Frontend (`cd web` first):

```bash
npm install
npm run dev                 # Next.js dev server (port 3000)
npm run build               # production build
npm run test                # vitest
```

Full app (both services):

```bash
./start.sh                  # installs deps, seeds skills, starts backend + frontend
start.cmd                   # same, on Windows (both wrap `node start.mjs`)
```

## Architecture: how a turn flows

1. **UI → backend.** A chat tab posts to the TS backend. Each tab carries its own `sessionId` (a Pi JSONL session); requests are scoped to a project via the `X-Project-Id` header (→ `?project` → `kady-project` cookie → `default`), resolved in an `onRequest` hook using `AsyncLocalStorage` (`server/src/scope.ts`).
2. **Sessions.** `server/src/agent/session-registry.ts` holds live Pi `AgentSession` objects (one per tab, ≤10 per project) and persists each as a JSONL file under `projects/<id>/sandbox/.pi/sessions/`. `ModelRuntime` + `ModelRegistry` are process singletons; the runtime uses Kady's shared Pi auth store.
3. **Models.** `server/src/agent/models.ts` resolves canonical `provider/model` refs (`openrouter/<vendor>/<model>`, `ollama/<name>`, `openai-compatible/<id>`, or `<pi-provider>/<model-id>` for every other built-in Pi provider) to a Pi `Model`, synthesizing OpenRouter models from `web/src/data/models.json` pricing when not built in. **Every Pi provider is supported** (https://pi.dev/docs/latest/providers): `server/src/agent/provider-catalog.ts` is the single table of direct API-key / cloud-credential providers (Anthropic, OpenAI, Google, Vertex, Azure, Bedrock, Cloudflare ×2, NVIDIA NIM, Groq, Cerebras, Mistral, DeepSeek, Hugging Face, Fireworks, Together, Baseten, Vercel AI Gateway, OpenCode ×2, Kimi, Moonshot ×2, MiniMax ×2, Z.AI ×2, Qwen ×3, Xiaomi ×4, Ant Ling) with the env var(s) Pi reads, a billing class, and Settings field metadata; `provider-auth.ts` lists the OAuth logins (OpenAI Codex, Anthropic, GitHub Copilot, xAI, Kimi For Coding, OpenRouter, Radius). `anthropic`/`xai`/`kimi-coding` appear in both — one ref, and billing follows whichever credential Pi resolves; `openai-codex`/`github-copilot`/`radius` stay OAuth-only (`isOAuthOnlyProvider`). Direct refs are never split after the prefix (NIM, Hugging Face, Fireworks, Cloudflare `@cf/…` ids contain slashes) and resolve only through Pi's registry — an unknown id is an error, except NVIDIA NIM, whose ids are synthesized at $0 like Pi's own entries (`synthesizeUnknownIds`; a payg model synthesized at $0 would bypass the spend cap). `provider-catalog.test.ts` checks the catalogue against the live runtime: every Pi provider covered, names match, and setting only the declared env vars flips `checkAuth` — so a Pi upgrade that renames a variable fails a test instead of leaving a dead Settings field.
4. **Streaming.** `POST /sessions/:id/run` calls `session.prompt()` and streams an SSE schema mapped from Pi's `AgentSessionEvent` (`server/src/agent/events.ts`): `text_delta`, `thinking_delta`, `tool_start/update/end`, `turn_start/end`, `error`, a terminal `cost` frame, and `done`. The run body may carry inline **image attachments** (`images: [{data, mimeType}]`, base64; validated by `server/src/agent/prompt-images.ts` — ≤12 × 5MB, png/jpeg/webp/gif) that ride the user message as Pi image blocks so the model sees them directly; the composer collects them via paste/drop/file-picker (`web/src/lib/image-attachments.ts` downscales >3MB client-side), other file types keep the sandbox-upload path, steering stays text-only (image sends mid-run queue instead), and `GET /sessions/:id/history` replays them for reopened tabs. The run route is a thin wrapper around `server/src/agent/run-pipeline.ts` (`claimRun` → `openRun` → `executeRun`: claim before the first await, `run_start` before model setup, ledger before the in-flight budget entry is dropped). A permanent per-session observer (`server/src/agent/session-observer.ts`, hooked in via `setSessionObserver`) reuses that pipeline to adopt turns Pi extensions start on an idle session (pi-subagents supervisor requests, scheduled-run and completion notices arrive as `pi.sendMessage` custom messages with `triggerTurn: true`) as **system runs** (`RunMetadata.origin: "system"`, ended on `agent_settled`, aborted when over the cap); a custom message with no turn becomes a `kind: "notice"` run. Custom messages (`role: "custom"`) reach the client as `message_start` frames carrying `customType`, text and a per-type whitelist of scalar `details` (`CUSTOM_MESSAGE_DETAIL_KEYS` in `events.ts`), appear in history as `role: "system"`, and render as `SystemCard`s; idle tabs poll `run/state?frames=0` to attach to runs they did not start.
5. **Cost ledger + budgets.** Pi reports `usage.cost` inline (no async backfill). `server/src/cost/ledger.ts` snapshots `getSessionStats()` before/after each run and appends a row to `projects/<id>/sandbox/.kady/runs/<sessionId>/costs.jsonl` (role `agent`|`subagent`|`compute`). `server/src/cost/billing.ts` classifies OpenRouter/API-key and Anthropic OAuth usage as cap-counted, while OpenAI Codex/Copilot/xAI subscription runs retain tokens plus `listPriceUsd` with `costUsd: 0`; provider quotas and overages remain external. Durable Modal jobs reserve their strict worst-case estimated cost before admission; project summaries expose spent/reserved/committed USD, and every terminal path reconciles the hold to estimated sandbox wall-time. A project `spendLimitUsd` blocks only cap-counted work when the new commitment would exceed the cap.
6. **Provenance.** The run loop attaches a `ProvenanceRecorder` (`server/src/provenance/recorder.ts`) to the same `session.subscribe` stream the SSE mapper reads, and appends one observed step per tool call to `sandbox/.kady/provenance/<sessionId>/steps.jsonl`. Rows are **derived from observation, never model declaration** — there is deliberately no agent-facing tool that writes here, because provenance is what you check the model against. `write`/`edit`/`read` name their file (edges `observed`); `bash`/`subagent`/unknown tools are opaque and get a bounded stat-only sandbox scan-diff (`server/src/provenance/scanner.ts`), whose edges downgrade to `inferred` when a neighbouring step finished before the scan ran. Scans are async-drained so the event handler never blocks SSE for other tabs; `flush()` in the run's `finally` drains before the terminal frames. Budgets (20k files, 512MB/file hash, 200 edges/step) degrade *visibly* — `sandbox-too-large`/`scan-failed`/`unhashed`/`truncatedEdges` — since silent truncation reads as a verified absence of outputs. `server/src/provenance/lookup.ts` inverts the log by path for `GET /sandbox/provenance`, computing staleness (current/stale/unknown) and flagging notebook citations written before an artifact's latest version. Subagent work is harvested from each child's session JSONL on completion (`server/src/provenance/harvest.ts` + `bridge.ts`, same `tool_result`/`subagent:async-complete` hooks as the notebook harvest and cost ledger) and appended to the parent's log with `role: "subagent"` and the child's agent name/model — no tool is installed in the child, so it stays unauthorable. Because that work is inspected *after* it finished, harvested refs are marked `identityAt: "harvest"` (a matching hash then proves only "unchanged since we looked", so `lookup.ts` reports `unknown`, never `current`), `change` is `wrote` rather than a created/modified guess, and a child's opaque `bash` gets `degraded: "no-scan-baseline"` plus optional mtime-window `inferred` edges filtered by already-claimed paths. Three further step sources join the same log: **user steps** (`server/src/provenance/user-steps.ts`, `role: "user"`, pseudo-session `user-actions`) are recorded by the sandbox routes for upload/save/move/delete so lineage chains have a root and an editor save is a recorded producing step rather than an unexplained "stale"; **compute steps** (`modal-steps.ts`, `role: "compute"`, id `modal:<jobId>`) are written at the Modal manager's single terminal transition from the transfer layer's own staging/collection hashes (observed, write-time — no harvest caveat); and every lead step carries an **`environmentId`** pointing at a content-addressed snapshot in `.kady/environments/` (`environment.ts`: venv `pyvenv.cfg` + `dist-info` names with no subprocess, one bounded `Rscript` probe when present, lockfile hashes, git HEAD), captured at run start and re-captured when an install-shaped command ran or the stat fingerprint of lockfiles + venv changed (`uv.lock` and `.venv` are invisible to the scan, so the diff alone misses `uv run` syncing a venv); harvested steps get a harvest-time snapshot marked `environmentAt: "harvest"`. Opaque calls also get `inferred` **input** edges from files their command line names that existed beforehand and were not written (`mentions.ts`), which is what lets `lookup.ts`'s `walkLineage` walk figure → script + table → upload; the walk is version-aware (producer at-or-before the consuming step) and reports `changedSinceUse` per upstream node. Tests that build a `ProvenanceRecorder` should pass `captureEnvironment: false` (or a stub) so they do not spawn probes. Not yet covered: nested (depth > 1) subagents, remote image package enumeration — see `docs/provenance.md`.
7. **Skills.** Two scopes: per-project `sandbox/.pi/skills/` and user-level `<agentDir>/skills/` (`~/.kady/pi-agent/skills`), both loaded by Pi — the latter also reaches subagent child processes. Pi resolves project entries first and skill-name collisions are first-wins, so **a project skill shadows a global one**; the Settings list labels that. Every origin is fetched through the bundled **`skills` CLI** (vercel-labs/skills) by `server/src/agent/skills-fetch.ts`, which downloads into a disposable staging cache (`KADY_SKILLS_CACHE_DIR`, default `~/.kady/skills-cache`) shaped as `.pi/skills/<name>/` because `-a pi --copy` targets exactly our layout. The CLI is a **fetcher only** and its stdout is never parsed (truth = the staged tree + `skills-lock.json`); `skills-sync.ts` remains the sole writer of live skill dirs, so tree hashing, the default-disabled policy, atomic per-skill replacement, local-edit preservation and archive-on-removal all survive unchanged. Catalogue seeding falls back to a shallow `git clone` if the CLI fails, since it is on the first-run path. The catalogue (`KADY_SKILLS_REPO`, default `K-Dense-AI/scientific-agent-skills`) syncs at launch and daily (`KADY_SKILLS_SYNC_INTERVAL_MS`, min 60s) and is **project-scoped only**. Manifest v2 (`.kady/skills-sync.json`, migrated from v1 rather than discarded) adds a per-skill `origin` (`catalogue`/`registry`/`local`) plus recorded source/ref, a content `catalogueDigest` replacing the commit id (staging is not a checkout), and `removed` tombstones so deleting a catalogue skill isn't undone by the next sync. `skills-install.ts` owns preview→install (the confirmed preview returns a `stagingToken` so the user installs the bytes they reviewed; the acknowledgement is enforced server-side), authoring from a template with Pi's stricter name rule, in-place `SKILL.md` editing, origin-aware removal, and on-demand update checks — user-installed skills are **never** auto-updated. Routes live in `server/src/api/skills.ts` (`?scope=project|global`); `GET /skills` merges both scopes for the composer picker so it agrees with what the agent loads. UI: `web/src/components/skills-panel.tsx`. See `docs/skill-management.md`. Live sessions keep their already-loaded skill set.
   **Prompt templates + slash commands.** `/skill:<name> args` and `/<template> args` on the first line of a chat message are expanded by Kady, not Pi (`server/src/agent/prompt-expansion.ts`, ports of Pi's `parseCommandArgs`/`substituteArgs` plus "append unused args"), read fresh from disk (project entries win), and `session.prompt()` is called with `expandPromptTemplates: false`; `/steer` and `/follow-up` expand too. The skill block is byte-identical to Pi's so `parseSkillBlock` works; templates expand to `<prompt-template name=…>`, and the web `command-blocks.ts` renders both as chips. Templates live in `sandbox/.pi/prompts/*.md` and `<KADY_PI_AGENT_DIR>/prompts/*.md` (`agent/prompts.ts`, routes `api/prompts.ts`, Settings → Prompt templates; five scientific templates seeded once per project, marker-gated). `disable-model-invocation` is exposed on `GET /skills` and toggled line-wise via `POST /skills/:name/model-invocation` (`setSkillModelInvocation`); the composer's pinned-skill picker hides such skills and the `/` menu offers them.
8. **Sandbox API + scientific previews.** `server/src/api/sandbox.ts` ports all file ops (tree/read/write/move/upload/zip/raw/download), annotation sidecars, LaTeX compile (async latexmk/multi-pass with SyncTeX), `/sandbox/synctex` (source<->PDF mapping), and the budget-gated `/sandbox/latex-assist` one-shot AI endpoint (ledgered under session id `latex-assist`). It also serves rich previews for many scientific formats. The frontend has an extensible viewer registry: `web/src/lib/viewers/registry.ts` maps a `FileCategory` (`web/src/lib/use-sandbox.ts`) to a lazy-loaded viewer in `web/src/components/viewers/*`; `FileViewer` in `file-preview-panel.tsx` checks the registry first and falls back to its built-in chain for the original categories (image/pdf/markdown/csv/notebook/fasta/biotable/latex/text). Binary/parse-heavy formats decode in **standalone Python helpers** under `server/src/helpers/` (`anndata_helper.py`, `chem_helper.py`, `structure_helper.py`, `massspec_helper.py`, `arrays_helper.py`, `imaging_helper.py`). They run in a dedicated **uv-managed helper venv** (`server/src/helpers/pyproject.toml`, `.venv`), resolved via `helperPython()` and pre-warmed by `syncHelperVenv()` (`server/src/helpers-env.ts`) at `prep`/boot. A generic dispatcher (`server/src/api/sci-helpers.ts`, `sciHelperFor`/`runSciHelper`) routes a `kind` param to a helper's `summarize`/`render` subcommands over two endpoints: `GET /sandbox/sci-summary?path=&kind=` (JSON) and `GET /sandbox/sci-render.png?path=&kind=&index=&axis=` (image); all helpers share the exit-code contract `0` ok / `3` deps-missing / `4` not-found / `5` bad-value / `1` other, mapped to HTTP by the routes. 3D structures also use a client-side WebGL viewer (3Dmol.js) and spectra use chart.js. New scientific viewers are view-only; user-facing coverage is in `docs/file-previews.md`.

## Configuration

- API keys come from `process.env`, auto-loaded by `server/src/env.ts` from (in order) repo-root `.env`, the legacy `kady_agent/.env` if present, and `server/.env`. `OPENROUTER_API_KEY` is optional when model access comes entirely from OAuth, a direct provider key (any env var in `provider-catalog.ts`, e.g. `ANTHROPIC_API_KEY`, `GROQ_API_KEY`, `AZURE_OPENAI_API_KEY` + endpoint, AWS credentials for Bedrock), or Ollama; Fusion and server-side speech remain OpenRouter-only. `server/src/api/credentials.ts` generates one managed `.env` entry per distinct catalogue env var (several providers share one: `MOONSHOT_API_KEY`, `OPENCODE_API_KEY`, `CLOUDFLARE_*`; `GEMINI_API_KEY` is both the web-search key and Pi's `google` provider key), so Settings → API keys → "Direct model providers" (`GET /providers`, fields from the catalogue) can set every one live; non-secret configuration values (regions, account ids) skip the 8-char minimum and are echoed unmasked. Other knobs include `OLLAMA_BASE_URL`, `DEFAULT_MODEL_PROVIDER`, `DEFAULT_MODEL_ID`, `KADY_PORT`, `KADY_PROJECTS_ROOT`, and `NVIDIA_EXTRA_MODELS` (comma/whitespace-separated NIM model ids absent from Pi's catalogue — e.g. private/EA endpoints — pinned into the picker's NVIDIA NIM section; ids verbatim, no `nvidia/` ref prefix). `start.mjs` keeps its own copy of the key variable names for the "no model access" launch warning.
- **Fusion pricing.** `buildFusionModel` prices a turn as each panel model once **plus the judge twice** — OpenRouter bills "N panel calls + 1 judge call in addition to your normal request", and under the `openrouter/fusion` alias that fusion-bridge.ts always sends, the judge also writes the final answer. The multiplier (`JUDGE_CALLS_PER_TURN`) and the judge accessor exist twice, in `server/src/agent/models.ts` and `web/src/lib/fusion-presets.ts`, because the picker quote and the ledgered price must agree; `server/test/fusion-pricing.test.ts` has a parity check over the shipped presets. Partly-priceable configs still run (under-counting, flagged in the picker); only a wholly unpriceable one throws.
- **Local model servers.** Two parallel discovery paths, deliberately not factored together: Ollama (`/ollama/models` → `OLLAMA_BASE_URL/api/tags`) and any OpenAI-compatible server (`/openai-compatible/models` → `OPENAI_COMPATIBLE_BASE_URL/v1/models`, default LM Studio's `:1234`). The latter's picker section stays hidden unless the env var was set (`configured`) or a server answers. Only `id` is read from `/v1/models`; refs are `openai-compatible/<id>` and may contain slashes, so only the prefix is stripped. Both providers are billed `local`/$0 in `cost/billing.ts`, `cost/ledger.ts`, and `agent/subagent-bridge.ts` — that trio must stay in sync or a local run defaults to `payg` and counts against the spend cap. Local-only by design: a hosted gateway would need real pricing, so route those through `OPENROUTER_BASE_URL` instead.
- **Outbound proxy.** `server/src/http-proxy.ts` installs undici's `EnvHttpProxyAgent` as the global dispatcher at boot (`index.ts`, `isMain` block) when `HTTP_PROXY`/`HTTPS_PROXY` is set, and is a no-op otherwise. Node's fetch ignores those variables on its own (`NODE_USE_ENV_PROXY` is Node ≥ 24 and we support ≥ 22.19), and Pi's `configureHttpDispatcher` isn't in the package's public exports — without this the lead agent would dial providers directly while the subagent runner honoured the proxy. Note undici tunnels with `CONNECT` even for `http://` targets.
- Pi OAuth tokens default to `~/.kady/pi-agent/auth.json`. `KADY_PI_AGENT_DIR` relocates that app-scoped directory; an explicitly supplied `PI_CODING_AGENT_DIR` takes precedence and can intentionally share a standalone Pi directory. The value is inherited by child `pi` processes, so lead and subagents share one auth store.
- Settings exposes API keys (`/credentials`) plus Pi subscription authentication (`/model-providers`, `/model-auth/flows`) for OpenAI Codex (ChatGPT Plus/Pro), Anthropic (Claude Pro/Max), GitHub Copilot, and xAI. OAuth browser/device/manual prompts are mediated by `server/src/agent/provider-auth.ts` and `server/src/api/model-providers.ts`. MCP servers, native web search (pi-web-access), and **durable Modal remote compute** (hybrid tools + per-chat selector + project Compute tab) are also implemented. **Not built in:** automated citation verification, first-party literature search, and document conversion (MCP connectors are the extension point).

**Capability hub.** **Model providers**, **Skills**, **Specialists** (subagents), and **Connectors** (MCP) live as tabs inside the **Settings** dialog (`web/src/components/settings-dialog.tsx`, opened from the header gear), alongside API keys / Fusion / Appearance — there is no separate customization surface. Enable/disable is non-destructive: skills move between `sandbox/.pi/skills/` and `sandbox/.pi/skills-disabled/`, project specialists between `sandbox/.pi/agents/` and `sandbox/.pi/agents-disabled/`, and MCP entries between `sandbox/.pi/mcp.json` and `sandbox/.pi/mcp-disabled.json`. Builtin (pi-subagents package) specialists are disabled via `subagents.agentOverrides.<name>.disabled` in `sandbox/.pi/settings.json`. Sessions read only the canonical locations, so toggles apply to new chat tabs/subagent runs (live sessions keep their set).

## Releases

- `server/package.json` `version` is the single source of truth for the app version. The web build reads it at build time (`web/next.config.ts` injects `NEXT_PUBLIC_APP_VERSION`); `web/package.json` deliberately has no `version` field.
- Releasing = bump `server/package.json` version and push/merge to `main`. The `Release` workflow (`.github/workflows/release.yml`) runs on every push to `main`, and if the tag `v<version>` doesn't exist yet it creates it plus a GitHub release with auto-generated notes. No manual tagging.

## Caveats worth knowing

- **One flat agent.** For independent/parallel subtasks the agent calls the `subagent` tool from the **pi-subagents** package. Children are **native Pi `AgentSession`s, not spawned `pi` CLI processes**: a background (`async`) child runs inside a detached runner process that pi-subagents starts from our installed `@earendil-works/pi-coding-agent` package and that loads the sandbox's ambient packages; a foreground (`async: false`) child would run inside the server process and, by design, load **none** of them. Every tool Kady hands a child is an ambient package (kady-notebook, kady-modal, kady-pdf-annotations, pi-web-access), so `server/src/agent/subagent-runtime-settings.ts` seeds `subagents.forceTopLevelAsync: true` (write-if-missing) to keep every launch in the runner. MCP tools are lead-only (`agent/mcp.ts` wraps them as Pi custom tools in the lead session; there is no child package). The runner exports `PI_SUBAGENT_CHILD=1` (our packages self-gate on it) but no per-child identity variables — several children share one runner process — so `subagent-child-identity.ts` learns a child's session file / id / name at `session_start`; kady-modal stamps jobs with `subagent_session_file` (the same `results[].sessionFile` key the ledger, notebook and provenance harvests correlate on) and kady-pdf-annotations derives the author from the `<agent>: <task>` session name. Specialist scientific agents are seeded into each project's `sandbox/.pi/agents/*.md` from `server/src/agent/subagents.ts` (write-if-missing; user edits win). Budget gating + cost ledgering for child runs lives in `server/src/agent/subagent-bridge.ts`.
- **`workflowScript` is the only delegation surface.** The `subagent` tool takes one execution parameter — a `workflowScript` JavaScript string declaring children as `runs.run(key, { agent, task })`; top-level `agent` only addresses management actions, and top-level `model` is a per-run override forwarded to every child. Walking the tool input structurally sees nothing under that surface, so the guards in `subagent-bridge.ts` use `workflowScriptTargets()`, which reads the `agent:`/`model:` literals out of the script. It also reports `dynamic` when a name is computed: gating still widens on a partial list, but `pinWorkflowScriptModel` refuses to pin at all, because a per-run `model` outranks agent frontmatter, `agentOverrides.<name>.model`, and `subagents.defaultModel` (all checked first — see `settingsPinnedModels`). Launches default to **async**, so the lead's tool allowlist in `session-registry.ts` must carry the wait tool **`bg_wait`** alongside `subagent` or Pi filters out its only way to block on the children it started (the pre-rename `subagent_wait` stays in the allowlist as a harmless rollback guard). pi-subagents also ships six **external-CLI builtins** (`claude-code`, `codex-exec`, `cursor-agent` and their `-writer` variants) that shell out to a locally installed and authenticated Claude Code / Codex / Cursor CLI, outside Kady's model runtime, ledger and spend cap; `subagent-runtime-settings.ts` seeds `agentOverrides.<name>.disabled: true` for them (write-if-missing, detected via `isExternalCliAgent`), so they show up off in Settings → Specialists and stay however the user toggles them.
- **Builtin tool overrides are reconciled, not just extended.** Builtin specialists pin a `tools:` allowlist that Pi also applies to package tools, so three bridges (notebook → modal → pdf-annotation, in that order) copy the declared list into `subagents.agentOverrides.<name>.tools` with their own group appended. That copy goes **stale** when an upstream release narrows a builtin (e.g. dropping `bash`/`edit`/`write` from `reviewer`): a settings file seeded earlier would hand the removed tools back. `server/src/agent/builtin-tool-overrides.ts` decides ownership by shape (drop tools the builtin no longer declares and that are not ours; does the remainder match something we generate?) and rewrites from the *current* frontmatter. A hand-written allowlist does not match and is left alone; a user addition to a Kady-shaped list is indistinguishable from an upstream removal and is dropped, which is the safe direction.
- **Interview tool (clarifying questions).** The `interview` custom tool (`server/src/agent/interview.ts`) blocks the run on a pending-answer promise; the questions ride the normal `tool_start` SSE frame and the chat UI renders them as an inline form (`web/src/components/interview-form.tsx`), POSTing answers to `/sessions/:id/interview/:toolCallId`. Tool `promptGuidelines` + the seeded `AGENTS.md` push the agent to interview liberally before assuming. Question schema mirrors pi-interview (single/multi/text/image/info, recommended/conviction/weight, code `content`, image/table/mermaid/chart/html `media`); user-uploaded images return to the model as image blocks. Deliberately NOT exposed to sub-agent child processes — they are headless and must not block on user input.
- **Thinking level.** Each chat tab has a per-run thinking-level selector (`web/src/components/thinking-selector.tsx`, default `high`); the run body's `thinkingLevel` is validated by `server/src/agent/thinking.ts` and applied via Pi's `session.setThinkingLevel()` after `setModel`. Ollama and Fusion runs send no level (chip disabled). Caveat: like `setModel`, Pi's `setThinkingLevel` also persists the value as the **global default** in the configured Pi agent directory (`~/.kady/pi-agent/settings.json` by default), so the last level picked in any tab becomes the starting level for subagent child `pi` processes. It also affects the user's standalone Pi CLI only when `PI_CODING_AGENT_DIR` was explicitly shared. Pin a `thinking` level in a specialist's frontmatter if a subagent must not inherit it.
- **Durable Modal remote compute.** The lead always registers the hybrid tools in `server/src/agent/modal-tool.ts`; submission reports `NOT_CONFIGURED` until a token pair is validated in Settings. `server/src/modal/manager.ts` owns persistent jobs under `.kady/modal/`, strict budget reservations, abort-safe sandbox creation, bounded logs, fallback resources, recursive/checksummed staging, atomic output installation, retry, batches, and restart recovery through saved sandbox ids. `server/src/modal/catalog.ts` is the sole CPU/GPU and estimated-price catalogue (including multi-GPU strings through B200); the UI reads it from `/modal/instances`. Things that are easy to get wrong here: the sandbox lifetime is `sandboxLifetimeSec` (command timeout **plus** a bounded transfer headroom) and the reservation, the reconcile cap and the recovery deadline all use it while the wrapped command gets exactly `timeoutSec`; input hashing happens at execute time (`planInputs` is stat-only, `hashInputPlan` streams), so `ModalTransferFile.sha256` is optional and a job that never ran has no input digest; uploaded inputs and produced outputs are re-hashed inside the sandbox (`verifyStagedInputs`, `collectOutputs`) with manifests passed as files, and the test fakes in `server/test/helpers/` emulate those `python3 -I -c` calls; `.kady`/`.pi`/`.kady-job` are skipped in the remote output walk *and* re-checked at install; every SDK error passes through `classifyModalError` and `NON_FALLBACK_ERROR_CODES` decides whether the fallback chain continues; the worker chain in `schedule()` always reconciles after a failure and ends in a logging `.catch`; recovery terminates tagged orphans (`findByTags`) and any terminal job's surviving sandbox; logs sync by the wrapper's `.meta` offsets, never by overlap search. `staging/outputs` under a job directory is the retained, verified copy that evidence packages and robustness workflows read — never prune it. A project Modal Volume is cache-only and optional named environments publish reusable images; the local sandbox remains canonical. Child `pi` processes receive the same tools from `server/pi-packages/kady-modal`, which calls the localhost project API so credentials and accounting stay centralized. Costs are estimates, not Modal invoice reconciliation; see `docs/modal-compute.md`.
- **Living Lab Notebook (`notebook`).** The lead agent uses an in-process `notebook` custom tool (like `interview` and `modal_run`) to write entries live to the notebook. Subagents get the tool via the vendored `kady-notebook` Pi package (referenced from `sandbox/.pi/settings.json`, like pi-web-access); the package registers the tool only in child processes (gated on `PI_SUBAGENT_CHILD` env var) so it never collides with the lead's tool. When a subagent finishes, its notebook entries are harvested from its session JSONL file, role-stamped with the agent name, and appended to the parent notebook (the parent is the single writer). Subagent entries appear batch-on-completion, not live token-by-token; the Lab Notebook view also polls `GET /sessions/:id/notebook` (~5s, backing off) while async subagent work is outstanding, so late entries surface without a reload. Nested subagents (depth > 1) are not harvested. Entries support threading (`relatesTo` + `stance` supports/refutes/neutral, `supersedes` for append-only amendments; both schemas — `server/src/agent/notebook.ts` and `server/pi-packages/kady-notebook/index.ts` — are deliberate duplicates guarded by a parity test, and `notebook-harvest.ts` namespaces child link ids like entry ids). Each `/run` mints a `runId` (`server/src/agent/run-ids.ts`, set/cleared in the run route, emitted as a synthetic `run_start` SSE frame) that stamps entries server-side for run dividers; async completions remain unstamped rather than borrowing a later run's id (durable launch correlation is still deferred). User pins/comments/notes live in a sidecar `sandbox/.kady/notebook/<sessionId>.annotations.json` (`GET/PUT /sessions/:id/notebook/annotations`, If-Unmodified-Since/412 like the sandbox file annotations). Export supports `format=md|json|zip` (zip bundles artifacts via adm-zip); `GET /projects/:projectId/notebook` merges all sessions for the project-scope view; `POST /sessions/:id/notebook/methods-draft` is a budget-gated one-shot AI draft (clone of latex-assist, ledgered under session id `methods-draft`, writes `methods_draft_<sessionId>.md` into the sandbox).
- **Evidence-aware notebook.** `evidence: [{entryId, sessionId?, relation, rationale?}]` adds multiple supports/challenges/inconclusive/context links, plus `outcome` and `limitations`; legacy relatesTo/stance still works. Shared pure semantics live in `web/src/lib/notebook-evidence-core.ts` (the server imports it too; keep it IO/framework-free and inside web's Turbopack root). All active evidence determines labels, never latest-entry-wins; superseded observations are excluded without inheriting links. `server/src/agent/notebook-artifacts.ts` captures citation-time hashes for new lead entries and derives bounded direct-artifact checks at GET/export time (25 citations/entry, 100 files/read, 8 MiB/file, 32 MiB total). Hashes are server-only fields and are not historical file copies; legacy/child citations remain unverified without write-time evidence. Project entries are keyed by session+id, the default project view merges active-chat entries live and polls other chats, and refresh failures are visible. `docs/notebook-roadmap.md` maps the six notebook features below to their docs.
- **Frozen plans and structured results.** User-reviewed frozen plans and deviations (`server/src/agent/notebook-plans.ts`, exclusively published event files under `.kady/notebook/plans/<source-hash>/`; preview token + dataset recheck + head preconditions, no agent-facing approval tool). `analysisPlan` is only a model-authored draft. `results` references canonical persisted `scientific_result` envelopes; `notebook-results.ts` performs bounded lookup and pins server-derived content digests, refusing changed replacements and child-local/parent-id collisions. Shared plan protocol lives in `web/src/lib/notebook-plans.ts`; nested lead/child input schemas live in the self-contained vendored `plan-schema.ts`. Routes are in `api/notebook-research.ts`; explicit missing project headers are rejected rather than falling back to default for approval/result operations. GET/export enrichments never trust tool-authored approval metadata. These local records are not external preregistration, an execution guard, or a same-user shell security boundary.
- **Robustness workflows.** `notebook.robustness` proposals and the user-only **Stress-test finding** approval UI (`notebook-robustness-dialog.tsx`). `agent/notebook-robustness.ts` owns immutable project-bound previews/private input snapshots and all specification records; `modal/manager.ts.submitApprovedBatch` reserves/persists the entire stable-id batch before a shared admission gate permits remote work. Server-only `ModalJob.approval` binds requests and input hashes; generic retry is refused for these jobs. Workers verify snapshots and actual uploaded bytes, retain every failed/missing/QC-excluded attempt, and read structured effects from checksummed transfer staging rather than mutable current outputs. Unknown launch/cleanup is conservatively counted at the full reservation; `modal/approval-reservations.ts` protects holds for missing committed job records. Startup and Modal credential restoration call robustness recovery after normal Modal recovery. Single backend remains the compute owner; this is not distributed exactly-once, an invoice cap, external preregistration or a same-user shell security boundary. `docs/notebook-robustness.md` covers the Python contract and limits.
- **Research memory.** Local read-only research recall (`agent/notebook-memory-loader.ts` + `notebook-memory.ts`, shared IO-free protocol/ranking in `web/src/lib/notebook-memory.ts`, UI `notebook-memory-dialog.tsx`). It reads bounded notebook windows, user notes and validated plan events fresh per query; source ids/digests, supersession, applicability (`scope`), `revisitWhen`, outcomes, incomplete coverage and direct artifact checks remain explicit. `notebook_search` is registered for lead and child sessions with visible search/read calls, no hidden prompt injection or new fact writes; the child's loopback `memory-client.ts` validates project context and does not follow redirects/proxies. All three builtin allowlist bridges recognize legacy and new notebook/search shapes; read-only provenance classification includes the tool. Tool text is capped at 24 KiB, clipboard recall at 16 KiB; full limits/privacy are in `docs/notebook-memory.md`. Hosted models still receive requested recall as normal context.
- **Evidence packages.** Human-reviewed evidence ZIPs (`server/src/evidence/*`, `api/evidence-packages.ts`, UI `evidence-package-dialog.tsx`). Preparation captures a bounded evidence/amendment graph, original source rows, selected annotations, plans/results/workflows, version-aware provenance and stored environments without probes. Versioned artifacts are matched against `.kady/evidence/blobs/<sha>` / retained compute copies / current bytes; current unverified copies require an explicit option. Immutable project-bound package previews include gaps, source-linked Methods scaffolding, base RO-Crate 1.1, checksums and a static `python3 -I verify.py`; packaging never runs analyses/models/compute or claims reproduction. ZIP streams verify payload hashes, download checks SHA on server and browser, and `X-Content-SHA256` is CORS-exposed. Package removal retains the shared vault; explicit pruning removes only versions unreferenced by readable retained packages. Quotas: 128 MiB/artifact, 256 MiB/package, 1 GiB vault, 20 packages / 2 GiB package storage; see `docs/evidence-packages.md`. `loadMemoryCorpus(..., {retainOriginal:true})` is opt-in for package/planning-history capture; raw source fields never enter memory-tool responses or planning-model prompts.
- **What next?** Planning proposals surface in `web/src/components/next-experiments-dialog.tsx` and are authored as structured `notebook.nextExperiments` note entries (shared IO-free `web/src/lib/next-experiments.ts`, vendored `next-experiments-schema.ts`). `agent/next-experiment-context.ts` selects bounded scientific context excluding proposals/preferences; `next-experiments.ts` generates only after explicit one-call approval and context-digest review, using no tools, with normal model billing under `next-experiments`. Local `next-experiment-receipts.ts` intent/outcome files prevent repeating confirmed or uncertain requests; invalid returned outputs are ledgered and never auto-retried. User prioritize/defer/reject preferences append exact proposal/context-bound decision records, not execution approvals. Proposal links are context only and cannot retire actual evidence; Methods drafts/scaffolds exclude them. Child refs are namespaced and harvest context stays unverified. Exports/memory/package graphs preserve qualified planning metadata and source gaps. See `docs/next-experiments.md` and `docs/lab-notebook.md`; no numerical information-gain optimizer, automatic experimentation, strict model-call reservation or provider invoice cap is claimed.
- **Model billing.** OpenRouter cost is read from Pi's `usage.cost` (computed from `model.cost`); synthesized model pricing comes from `web/src/data/models.json`. Pi-documented Anthropic OAuth metered extra usage also counts toward caps. OpenAI Codex, GitHub Copilot, and xAI OAuth usage records tokens/reference price without counting it as project spend; this is not a claim that provider usage is free, because quotas and overages are managed externally. NVIDIA NIM and the prepaid token plans (`qwen-token-plan*`, `xiaomi-token-plan-*`; `isPlanBilledProvider` in `provider-catalog.ts`) are classified the same way (`billingMode: "subscription"` despite being API-key-based): they bill provider-managed credits or a plan quota rather than per-token USD, Pi prices every such model at $0, and treating them as payg would let an exceeded spend cap block runs that ledger $0 (`provider-catalog.test.ts` asserts an all-$0 Pi catalogue is plan-billed and a mostly-priced one is not). Every other direct provider is payg with Pi's list price. OpenRouter/Radius OAuth logins are `payg` (they stand in for a key); the Kimi Code OAuth login is `subscription` while `KIMI_API_KEY` is payg. Picker rows carry the same `billingMode` from `directModelForClient`, and `/providers/models` skips a dual provider Pi resolved via OAuth so each model is listed once, under the billing its credential implies.
- **One-shot model calls must name a reasoning level.** Methods draft (`agent/methods-draft.ts`), What next? proposals (`agent/next-experiments.ts`) and editor LaTeX assist (`latex/assist.ts`) call `ModelRuntime.completeSimple(model, context, { maxTokens, reasoning: ONE_SHOT_REASONING })` (`agent/one-shot-reasoning.ts`), not `complete`. `complete` is the raw provider stream: with no effort given, Pi's OpenAI-compatible adapter sends OpenRouter `reasoning: { effort: "none" }` for every reasoning-capable model, and models whose reasoning cannot be disabled (GPT-6 Astra, the default) answer `400 Reasoning is mandatory for this endpoint and cannot be disabled` — chats were unaffected because a session always carries the tab's thinking level. `completeSimple` clamps the level to what the model supports, so the one constant is safe for non-reasoning models too. The three tests assert the option is passed.
- **Schedules + missions (server-owned).** pi-subagents arms schedule timers per live session and a fire produces no `tool_call`, so `server/src/agent/scheduler.ts` keeps one **resident session** per project with active schedules (id in `.kady/scheduler.json`, `markSystemSession` = pinned, excluded from `MAX_LIVE_PER_PROJECT`, hidden from `GET /sessions`), opened at boot and on `schedule.create|resume|run` via `setScheduleActivityListener` (a hook, because bridge → scheduler → registry would cycle). Panel actions and the budget hold call the `subagent` tool's `execute` directly on that session (`invokeSubagentAction`, no model). The bridge gates `schedule.create` like a launch and refuses `schedule.run`/`run-due` over the cap; `reconcileBudgetHolds` (60s tick, `startSchedulerTick` in the `isMain` block only — never in `buildApp`) pauses active schedules while over the cap (`heldByBudget`) and resumes them after. `subagent:async-complete` carries `scheduleOrigin`, ledgered as `CostEntry.origin.schedule` (`scheduleSpend`). `api/automation.ts` reads pi-subagents' store (`sandbox/.pi/subagents/schedules/<id>/{schedule,history}.json`, owner paths stripped) and missions (`<agentDir>/missions/projects/<sha256(sandbox)>/*.json`); UI is the project view's Automation tab (`automation-panel.tsx`). `AGENTS.md` v4 tells the lead to confirm interval/cost before scheduling.
- **Custom model servers (`models.json`).** `server/src/agent/custom-models.ts` manages Pi's `<KADY_PI_AGENT_DIR>/models.json` (`GET/PUT /custom-models`, Settings → Model providers → Custom model servers): validation (`CUSTOM_PROVIDER_ID_RE`, no collision with catalogue/OAuth/reserved ids, http(s) base URL, api ∈ openai-completions|openai-responses|anthropic-messages, models with optional USD-per-million cost), atomic write, then `ModelRuntime.refresh()` so the new provider is live without a restart. Kady rewrites only providers it created (sidecar `kady-custom-models.json`); hand-written providers are listed read-only and a same-id save is refused. `directProviderRef` in `models.ts` recognizes custom ids via `isCustomProvider` (mtime-cached) so `<id>/<model>` resolves through `registry.find` and an unknown id errors — the legacy "unknown prefix = OpenRouter vendor id" fallback is kept for stored refs. `/providers/models` appends custom rows (`sourceLabel: "Custom servers"`, `billingMode: "payg"`, declared cost) and lists the provider as configured, so the picker and `billing.ts` (payg default) agree. Keyless servers get `apiKey: "none"`, like Kady's own Ollama registration. `modelThinkingLevels` is deliberately not exposed (the tab's thinking level is applied after `setModel`).
- **Per-agent memory.** pi-subagents' `memory:` frontmatter is modelled in `agent-files.ts` as `AgentFile.memory` (`{scope: project|user, path}`), written only in the inline form `memory: { scope: project, path: x }` because the flat YAML-subset parser would otherwise flatten a block into `extra`; `restoreDefaultAgents` carries an existing memory setting onto the rewritten roster file. `GET/PUT/DELETE /agents/:name/memory` read/edit/clear `<sandbox>/.pi/agent-memory/<path>/MEMORY.md` (or the user-scope file under `KADY_PI_AGENT_DIR`); the child creates it itself with `write`. Harvested child writes under dot-directories are already dropped by `resolveInSandbox` (`isUserVisible`), so memory writes never become provenance artifacts.
- **Supervisor channel + watchdog.** pi-subagents' `contact_supervisor` (child) / `subagent_supervisor` (parent, now in the lead allowlist and in both provenance read-only sets) delivers a child's question as a `subagent_supervisor_request` custom message with `triggerTurn: true`; the session observer adopts that turn as a system run, the SystemCard shows it, and the seeded `AGENTS.md` (v3) plus the `interview` tool's guidelines tell the lead to relay via `interview` and answer with `subagent_supervisor` reply (child timeout ≈10 min). The watchdog is configured in `sandbox/.pi/settings.json` → `subagents.watchdog` through `server/src/agent/watchdog-settings.ts` (`GET/PUT /watchdog`; strict upstream key set, Kady always writes `lsp.enabled: false`, `WATCHDOG.md` seeded once with scientific rules); findings arrive as `subagent_watchdog_warning` custom messages. pi-subagents reports no watchdog usage, so that spend is unledgered — the Settings card says so; default off. `GET /projects/:id/instructions` reports `agentsMdStatus` and `POST …/restore` rewrites the shipped text.
- **Raw-data guard.** `server/src/agent/data-guard.ts` is a `tool_call` hook (registered after the subagent bridge so budget gates run first) that blocks `write`/`edit`/`bash` mutations of the project's protected globs (`sandbox/.kady/policy.json`, `guard-policy.ts`, default `user_data/**`) and, when `destructiveConfirm` is on, pauses destructive shell commands elsewhere via `permissions.ts`: a `permission_request` frame rides the run's `RunHandle`, the UI answers through `POST /sessions/:id/permissions/:requestId`, and abort/run completion/10-min timeout resolve it as a block. The classifier (`bash-classifier.ts`: segment split, `cd` tracking, redirects, mutating verbs, destructive patterns, benign `rm -rf` targets) is pure and copied byte-for-byte into `server/pi-packages/kady-guard/classifier.ts` for child processes (`bash-classifier.test.ts` runs the same table against both and asserts parity); the child package blocks destructive commands outright since it has no UI. `sandbox-seed.ts` now versions `AGENTS.md` (`AGENTS_MD_HISTORY`): a sandbox whose file equals an older shipped version verbatim is upgraded on the next seed pass, an edited file is left alone and reported by `agentsMdStatus`, and `restoreAgentsMd` is the explicit restore. Heuristic, not a security boundary — see `docs/data-guard.md`.
- **Compaction is science-aware.** `server/src/agent/compaction-bridge.ts` hooks Pi's `session_before_compact` and returns a full `CompactionResult`: a deterministic preamble built from Kady's stores (`buildCompactionPreamble`: notebook entries, latest frozen plan, `scientific_result` step ids, latest `environmentId`) followed by a narrative generated with Pi's exported `generateSummaryWithUsage` under `SCIENCE_COMPACTION_INSTRUCTIONS`; split turns get a second call like Pi's own. Returned `usage` lands on the compaction entry and in `getSessionStats()`, so it is ledgered. Any failure returns `undefined` (Pi's default runs); the hook never cancels. `POST /sessions/:id/compact` is the manual path (409 while streaming/claimed, 402 over cap, ledgered from the stats delta); `GET/PUT /projects/:id/compaction` edits `compaction.*` in `sandbox/.pi/settings.json` via `compaction-settings.ts` (malformed file → 409, never rewritten). `compaction_end` reaches the client as a `customType: "compaction"` frame.
- **Provider refusals are explained, not swallowed.** Anthropic's Mythos-class models classify the *whole* request before generating; Claude Fable 5 refuses outright when the skills index in the system prompt carries certain seeded scientific skills (`adaptyv`, `diffdock`, `ginkgo-cloud-lab`, `glycoengineering`, `pathogen-variant-surveillance`, `phylogenetics`, `tamarind` — each verified to refuse on its own description, 2026-08-27). The wire signal is `stop_reason: refusal` / OpenRouter `finish_reason: content_filter` with **no `usage` object at all**, which is why such a run reports zero input tokens and bills nothing. It is a model-level behaviour reproducible with a bare chat-completions call, not a Kady bug, and it hits the lead agent as well as subagents (children inherit the lead's model). `server/src/agent/model-refusal.ts` recognizes the signal and builds the guidance; `events.ts` forwards the provider's own `errorMessage` rather than a generic `Model error`, `api/sessions.ts` appends the guidance to both provider-error publish points, and `makeSubagentRefusalExtension` appends it to a refused child's `subagent`/`bg_wait` result — a child dies in its own session inside pi-subagents' runner process, so runner text is the only trace that reaches the parent. `KNOWN_REFUSAL_TRIGGER_SKILLS` is used **only** to make an error message specific: never to block, disable, or filter, because it is empirical and providers retune classifiers. See `docs/limitations.md`.
- **Local shell trust boundary.** Agent tools run as the current OS user and are not an OS-level secret boundary. Kady-scoped `auth.json` is protected from other users, not from same-user shell processes. New sandbox instructions forbid reading credentials, but use a container/VM/separate account for adversarial content; see `docs/limitations.md`.
- **The harness is pinned to exact versions.** `server/package.json` pins Pi (`@earendil-works/pi-{agent-core,ai,coding-agent}`, which share a version line) and the extension packages `pi-subagents`, `pi-web-access`, and `skills` to exact versions (no caret). `installBackendPackages()` in `start.mjs` reads those pins and installs them as explicit `name@version` specs on every full start, so a checkout with a stale or hand-edited lockfile still converges on the pinned set. Upgrading the harness is a deliberate act: bump the pins in `server/package.json` (Pi's three packages must stay on one version), run `npm install` in `server/` to move the lockfile, and re-run typecheck + tests before shipping — the `workflowScript` and builtin-tool-override caveats above are the class of upstream change that breaks silently if versions float.
- **Node ≥ 22.19** is what Pi targets; lower 22.x usually works but emits an `EBADENGINE` warning. Node < 22 (e.g. v20) fails to build/install the packages, so the launcher (`start.mjs`) refuses to run on it, on every platform.
- **Windows portability.** Sandbox-relative paths are canonicalized to forward slashes at the API boundary (`apiRelative`/`toApiPath` in `server/src/sandbox-fs.ts`, `stripSandboxRoot` in `server/src/agent/events.ts`) — the frontend always sees `/`-separated paths. External binaries are located via `server/src/binaries.ts` (`hasBinary`/`findUv`/`firstRunnable`), never `which`. On Windows the agent's `bash` tool uses Git Bash (Git for Windows is a hard prerequisite there), the helper venv interpreter lives at `.venv/Scripts/python.exe`, and synctex is invoked from the PDF's directory with relative paths so drive-letter colons stay out of its colon-delimited args in the primary invocation (`forwardArgs`/`inverseArgs` in `server/src/latex/synctex.ts`; a forward-slash absolute-path retry exists as a fallback for absolute `Input:` records).
- **Don't run our source through `tsc` for emit** — both dev and prod run via `tsx`; `tsconfig.json` is `noEmit` for typechecking only.
